# Drawer, composited from offscreen layers

## 1. Goal

An app should be able to put a sheet of controls behind an edge of its
screen and let the user pull it out with a finger, close it with a tap or
Back, and open it from a button, without writing the gesture, the animation
or the drawing itself. The motion should be smooth on a phone even when the
screens on both sides are expensive to draw.

After this plan:

- a `Drawer` owns a content `Router` laid out in the sheet's own
  coordinates, and a shareable `DrawerState` (phase, progress, drag,
  animation) that survives the drawer being rebuilt;
- the app offers every input event to the drawer first; the drawer says
  whether it took it, whether it took over a press the main screen had, or
  whether the main screen should have it;
- while the drawer is visible, the main screen and the sheet are each kept
  in an offscreen texture and redrawn only when they change; the frame is a
  composite of the two driven by one uniform, the eased progress `t`;
- while the drawer is closed (`t` is 0 and nothing moves it) it costs
  nothing on the GPU: the main screen draws straight to the surface exactly
  as it does today, with no texture, no extra pass and no copy (section 4);
- an app that does not set up the textures still gets a working drawer,
  drawn directly into its `DrawList` with a clip and a translate.

**Why textures.** libmsdf draws a whole `DrawList` in one full-screen pass
whose fragment shader loops over every command for every pixel
(sdf_render.wgsl:378), so a frame costs roughly pixels times commands. A
drawer transition is the worst case for that: both screens are on the
glass, and both move or dim every frame for 250-300 ms. Kept in textures,
a transition frame is one pass of two or three texture samples per pixel,
whatever the screens contain.

**Motivation in flankr.** The companion's settings replace the whole
screen (lib.rs:2595-2598, 2623-2627) and Back closes them (2471-2478). A
right-hand drawer would keep the overview or the agent's terminal visible,
dimmed, behind the settings; a left-hand drawer could list sessions over the
agent view. The terminal behind keeps updating, which section 3.7 covers.
These are examples only; this plan changes nothing in flankr.

## 2. Findings (read 2026-10-28)

- **Offscreen rendering already works in libmsdf.** Every
  `GpuSdfRenderer` render takes any `&wgpu::TextureView` as its target
  (gpu/mod.rs:579-650), and `BlurPass` (blur.rs:1-13) is exactly this
  pattern for Highbay's settings modal: the app view is rendered to a
  `backdrop` texture, the modal to a transparent `overlay` texture, and a
  self-contained pass composites them. libmsdf does not need a render-target
  feature.
- **There is no composite that moves things.** `BlurPass` blurs the
  backdrop and lays the overlay over it at the same place. Nothing offsets,
  scales or fades one layer over another by a parameter. The SDF
  pipeline's texture draw type (sdf_render.wgsl:546) samples `tex_array`,
  a 1x1 placeholder with no upload path (gpu/mod.rs:276), which could not
  hold a render target anyway. So the composite is a new wgpu pipeline,
  which by the owner's direction lives in libcontrols itself (section 3.9).
- **libcontrols can depend on wgpu directly at no cost.** It already
  compiles wgpu 30.0.1 through libmsdf (libmsdf Cargo.toml:13); libmorph
  uses the same 30.0.1 (Cargo.toml:63), and both lock files resolve one
  copy. A direct `wgpu = "30.0.1"` dependency in libcontrols adds no code
  to the build and pins nothing new; a later wgpu move must happen in
  libmsdf, libmorph and libcontrols together, as it already must for
  libmsdf and libmorph.
- **The renderer's targets must be in the surface format.** Its pipeline is
  built for the format it was created with, with `REPLACE` blending
  (gpu/mod.rs:464-465). The layer textures are created in
  `ctx.surface_format()` with `RENDER_ATTACHMENT | TEXTURE_BINDING`.
- **One renderer, one set of buffers.** Every render writes the same
  draw-command and uniform buffers with `queue.write_buffer`
  (gpu/mod.rs:1070, 1103), which take effect at the next `queue.submit`.
  Two lists recorded into one encoder with the `_into` variants would both
  draw the second list. Layers are therefore rendered with the variants
  that submit their own encoder, one after another; the composite may
  share the frame's encoder.
- **Clearing.** `render_draw_list_in` clears to opaque black
  (gpu/mod.rs:895); only the lower-level `render_full_scaled_clear_into`
  clears to transparent (1043), and libmsdf's convenience for it
  (`render_overlay_texture`, blur.rs:257) lowers with `lower()` and so
  ignores an `AtlasSet`, which the companion uses. The sheet's rounded
  corners need a transparent clear with the atlas set; libcontrols does it
  from public pieces: `list.lower_with(set)`, `upload_chars`,
  `upload_params`, then `render_full_scaled_clear_into` into its own
  encoder, submitted at once. libmsdf needs no change.
- **libmorph needs no change.** It hands the app the device, the queue,
  the surface view, its format and size every frame (app.rs:10, 87;
  context.rs:76-132), and the drawer takes them from the app as plain
  `wgpu` references. It reports a safe area but not Android's
  system-gesture insets (safe_area.rs:6), which matters for edge swipes
  (section 10, risk 1); that is optional and not part of this plan.
- **libcontrols has no easing.** `ModalTransition::Timed` moves progress
  linearly (modal.rs:43); the scroll pane's overscroll is a spring. The
  drawer brings its own curves (section 3.4).
- **The router can be told to let go of a press only from inside the
  crate** (`cancel_grab`, router.rs:1079). An app whose main screen is a
  `Router` needs a public way to end a press the drawer has taken over
  (section 3.8).
- **`ControlTheme` is exhaustive** (theme.rs:5): a `drawer` field would be
  breaking. This plan keeps the drawer's values in `DrawerOptions` so the
  release is additive (section 7; open question 2).
- **Dirty tracking.** libmsdf's `PaneMark` (pane.rs:94) is a revision
  counter that a write bumps; a reader records the revision it drew at. The
  layers use it rather than booleans, for the reason pane.rs gives: drawing
  can itself write, and a revision cannot be confused by that.

## 3. Design

### 3.1 Geometry and coordinates

- The drawer has a **viewport**, the main screen's rectangle in router
  pixels (normally the whole surface), and an **edge**:

  ```rust
  #[derive(Copy, Clone, Debug, PartialEq, Eq, Hash)]
  #[non_exhaustive]
  pub enum DrawerEdge { Left, Right, Top, Bottom }
  ```

- Its **extent** is the sheet's size across the edge:

  ```rust
  #[derive(Copy, Clone, Debug, PartialEq)]
  #[non_exhaustive]
  pub enum DrawerSize {
      /// A fixed size in router pixels, at most the viewport's.
      Px(f32),
      /// A share of the viewport across the edge, at most `max` pixels.
      Share { share: f32, max: f32 },
  }
  ```

  Defaults: Left and Right `Share { share: 0.85, max: 360.0 }` (M3's
  360 dp, at the router's scale as the other values); Top and Bottom
  `Share { share: 0.6, max: f32::INFINITY }`. The sheet spans the whole
  viewport along the edge.
- **The open sheet** `sheet_open: Rect` is the extent-wide strip against
  the edge. At progress `t` the sheet is `sheet_open` moved outward by
  `(1 - t) * extent`: for Left, `x = viewport.x - (1 - t) * extent`.
- **Content coordinates.** The content router is laid out with its origin
  at the sheet's top-left corner and its size the sheet's size, so the
  content never moves while the sheet does, and the sheet texture is only
  as large as the sheet. The drawer maps a viewport point `p` to content as
  `p - sheet(t).pos()`.
- The drawer draws the sheet's background itself (`DrawerOptions::sheet_color`,
  default the theme's `bg_color`, with `corner_radius` 16 px on the corners
  at the open edge) before the content, so the sheet texture is opaque
  except outside the rounded corners.

### 3.2 `DrawerState` and phases

```rust
/// One drawer's place and motion. Shared (`Arc`) between the drawer and the
/// app, like `ScrollState`, so it survives the drawer being rebuilt.
pub struct DrawerState { /* Mutex-guarded inner; Send + Sync */ }

#[derive(Copy, Clone, Debug, Default, PartialEq, Eq, Hash)]
#[non_exhaustive]
pub enum DrawerPhase {
    #[default]
    Closed,
    /// Animating towards open.
    Opening,
    Open,
    /// Animating towards closed.
    Closing,
    /// A finger holds the sheet.
    Dragging,
}

impl DrawerState {
    pub fn new() -> Arc<Self>;
    /// Starts open, at t = 1, with no animation.
    pub fn open_at_start() -> Arc<Self>;
    pub fn open(&self);                 // animates; DrawerReason::App
    pub fn close(&self);                // animates; DrawerReason::App
    pub fn toggle(&self);
    /// Jump without animating (restoring a saved layout).
    pub fn set_open_now(&self, open: bool);
    pub fn phase(&self) -> DrawerPhase;
    /// The eased progress, 0 closed .. 1 open: what is drawn, what the
    /// shader gets.
    pub fn progress(&self) -> f32;
    pub fn is_visible(&self) -> bool;   // phase != Closed
    pub fn is_moving(&self) -> bool;    // Opening, Closing or Dragging
    pub fn take_events(&self) -> Vec<DrawerEvent>;
}
```

It holds `t: f32`, the phase, the animation in progress (start time, start
`t`, target, duration, curve, start slope), the drag (pointer id is not
needed: one pointer per router, as the scroll pane; the start point, the
start `t`, recent samples on drawer time over the last 100 ms), the clock
(`time: f64`, the sum of `advance`), and the events not yet taken.

`open()` while Opening or Open, and `close()` while Closing or Closed, do
nothing. `open()` while Closing turns round from the current `t`; so does
`close()` while Opening. Neither does anything while Dragging (the finger
wins); the app can call `cancel_drag()` first if it must.

### 3.3 Events out

```rust
#[derive(Copy, Clone, Debug, PartialEq, Eq, Hash)]
#[non_exhaustive]
pub enum DrawerReason { App, EdgeSwipe, Drag, Fling, ScrimTap, Back, Escape }

#[derive(Copy, Clone, Debug, PartialEq)]
#[non_exhaustive]
pub enum DrawerEvent {
    /// Left Closed (an animation or a drag began).
    Shown { by: DrawerReason },
    /// Reached Open and settled; the content takes input.
    Opened { by: DrawerReason },
    /// Began to close, and why.
    Closing { by: DrawerReason },
    /// Reached Closed; the main screen takes input again. Every `Shown` is
    /// followed by exactly one `Hidden`, unless the app drops the drawer.
    Hidden { by: DrawerReason },
}
```

A drag that is released back to where it began reports `Shown` then
`Hidden` (from Closed) or nothing (from Open, as it never left Open's
side of the gesture: it reports `Closing` only when the release target is
closed).

### 3.4 Motion: the uniform `t`

`t` is a position, not a time. Three things move it.

**Programmatic** (`open`, `close`, a scrim tap, Back, Escape): an eased
curve from the current `t0` to the target.

| | Curve | Full duration `D` |
|---|---|---|
| Opening | M3 emphasized decelerate, cubic-bezier(0.05, 0.7, 0.1, 1.0) | 0.300 s (medium2) |
| Closing | M3 emphasized accelerate, cubic-bezier(0.3, 0.0, 0.8, 0.15) | 0.250 s (medium1) |

The duration is `max(0.120, D * |target - t0|)` seconds, so a half-open
sheet does not take as long as a closed one. At time `s` into it,
`t = t0 + (target - t0) * ease(s / duration)`.

**Dragging**: the sheet follows the finger one to one. With `d` the
finger's movement since the drag began, projected on the axis and signed
towards open (positive rightwards for Left, leftwards for Right, downwards
for Top, upwards for Bottom), `t = clamp(t_start + d / extent, 0, 1)`. No
easing is applied while dragging; there is no rubber band past 1 (the
sheet stops at open) or 0.

**Release**: on the finger lifting, with `v` the finger's velocity along
the axis towards open, in px/s, measured as the scroll pane measures it
(displacement over the last 100 ms of samples; zero if the finger rested
`rest` = 0.100 s before lifting):

- the target is open if `v >= fling_velocity`, closed if
  `v <= -fling_velocity`, and otherwise open if `t >= 0.5`, else closed
  (`fling_velocity` 400 px/s, Android DrawerLayout's 400 dp/s);
- the reason is `Fling` when the velocity decided, `Drag` otherwise;
- the sheet then moves to the target on a **velocity-matched ease**, so it
  leaves the finger at the finger's speed and settles without a jump. With
  `Δ = |target - t0|` and `w = |v| / extent` (t per second) when `v`
  points at the target, else `w = 0`:
  - `duration = clamp(3Δ / w, 0.120, max(0.120, D * Δ))` (`D` from the
    table for the direction; `3Δ / w` is infinite when `w = 0`);
  - `m0 = min(w * duration / Δ, 3.0)`, the normalised start slope;
  - `t = t0 + (target - t0) * h(u)`, `u = s / duration`, with the cubic
    Hermite `h(u) = m0 (u³ - 2u² + u) + 3u² - 2u³`. It starts at slope
    `m0`, ends at slope 0 and is monotonic on [0, 1] for `0 <= m0 <= 3`,
    so it never overshoots. With no velocity it is smoothstep.

**A touch during an animation** catches the sheet: a `Down` while Opening
or Closing stops the animation at the current `t` and starts a drag from
there at once, with no slop (a touch that stops a moving sheet is not a
tap), as a touch stops a fling in a scroll pane.

`DrawerState::advance(dt)` (called by `Drawer::advance`, with `dt` capped
at 0.1 s as the router caps it) moves the animation on and returns whether
anything still moves. Reaching the target sets Open or Closed exactly
(`t` is 1.0 or 0.0, not 0.9997) and queues `Opened` or `Hidden`.

The curves live in a small public module, `src/ease.rs`:

```rust
#[derive(Copy, Clone, Debug, PartialEq)]
pub struct CubicBezier { pub x1: f32, pub y1: f32, pub x2: f32, pub y2: f32 }

impl CubicBezier {
    pub const STANDARD: Self;               // (0.2, 0.0, 0.0, 1.0)
    pub const EMPHASIZED_DECELERATE: Self;  // (0.05, 0.7, 0.1, 1.0)
    pub const EMPHASIZED_ACCELERATE: Self;  // (0.3, 0.0, 0.8, 0.15)
    /// y at x, for x in [0, 1]: Newton's method on x(s), 8 iterations, then
    /// bisection if it has not converged to 1e-6.
    pub fn ease(&self, x: f32) -> f32;
}

/// The release curve above.
pub fn hermite_ease(u: f32, m0: f32) -> f32;
```

### 3.5 Options

```rust

    pub edge_inset: f32,               // 0.0

    pub open_duration: f32,            // 0.300 s
    pub close_duration: f32,           // 0.250 s

}

#[derive(Copy, Clone, Debug, PartialEq)]
#[non_exhaustive]
pub struct MainEffect {
    /// How far the main screen moves with the sheet at t = 1, as a share
    /// of the extent (0 = M3's modal drawer, 0.33 = a parallax push).
    pub shift: f32,                    // 0.0
    /// The main screen's scale at t = 1, about the viewport's centre.
    pub scale: f32,                    // 1.0
}

#[derive(Copy, Clone, Debug, PartialEq, Eq)]
#[non_exhaustive]
pub struct DrawerDismiss { pub scrim_tap: bool, pub back: bool, pub escape: bool, pub drag: bool }

#[non_exhaustive]

```

Each has a `Default` and `with_*` builders. Values are in router pixels and
seconds; an app drawing at a scale multiplies the pixel values, as it does
the theme's. The touch slop is the theme's `scroll.touch_slop` (8 px), as
for scroll panes: one slop in the crate.

`Drawer` is not a router node: the main screen may not be a `Router` at
all (the companion's overview and agent screens draw and route touches
themselves), so the drawer sits in front of whatever the app has.

### 3.7 Layers, textures and invalidation

`DrawerLayers` (src/drawer/layers.rs) is the GPU half, written against
`wgpu` directly. It owns the two textures and the composite pipeline
(section 3.9).

```rust
pub struct DrawerLayers { /* composite, main: Option<Layer>, sheet: Option<Layer>,
                             format, pipeline, sampler, uniform buffer,
                             bind group layout, main_mark: PaneMark,
                             main_drawn_at: Option<u64>, sheet_drawn_at: Option<u64>,
                             closed_for: f32 */ }

struct Layer { texture: wgpu::Texture, view: wgpu::TextureView, size: (u32, u32) }

#[derive(Copy, Clone, Debug, PartialEq, Eq)]
#[non_exhaustive]
pub struct LayerPlan {
    /// t is 0 and nothing moves it: draw the main screen straight to the
    /// surface, exactly as today. No texture is touched, no composite runs.
    pub direct: bool,
    /// Draw the main screen into `main_view()` this frame.
    pub draw_main: bool,
    /// Draw `Drawer::render_sheet` into `sheet_view()` this frame.
    pub draw_sheet: bool,
}

impl DrawerLayers {
    pub fn new(device: &wgpu::Device, format: wgpu::TextureFormat) -> Self;
    /// Bump when the main screen's drawing changes.
    pub fn main_mark(&self) -> &PaneMark;
    /// Decide this frame. Creates or recreates textures as needed and
    /// records the revisions it asks the app to draw at; the app must then
    /// draw what the plan says before `composite`.
    pub fn prepare(&mut self, device: &wgpu::Device, drawer: &Drawer,
                   surface: (u32, u32), scale: f32) -> LayerPlan;
    pub fn main_view(&self) -> Option<&wgpu::TextureView>;
    pub fn sheet_view(&self) -> Option<&wgpu::TextureView>;
    pub fn sheet_size(&self) -> (u32, u32);
    /// Draw `list` into the sheet texture, cleared to transparent, with
    /// `renderer` (lower_with(set), upload_chars, upload_params,
    /// render_full_scaled_clear_into into its own encoder, submitted).
    pub fn render_sheet(&self, device: &wgpu::Device, queue: &wgpu::Queue,
                        renderer: &GpuSdfRenderer, list: &DrawList, set: &AtlasSet);
    /// The one composite pass into the frame's target.
    pub fn composite(&self, device: &wgpu::Device, queue: &wgpu::Queue,
                     target: &wgpu::TextureView, drawer: &Drawer, scale: f32);
    /// Create the textures ahead of the first visible frame (section 4.3).
    pub fn prewarm(&mut self, device: &wgpu::Device, drawer: &Drawer,
                   surface: (u32, u32), scale: f32);
    /// Count time closed; free the textures after `keep_warm`.
    pub fn advance(&mut self, dt_secs: f32, drawer: &Drawer);
}
```

**A frame**, with the drawer visible:

```rust
let plan = layers.prepare(ctx.device(), &drawer, frame.size, s);
if plan.direct {
    /* draw the main screen to frame.view exactly as today */
} else {
    if plan.draw_main {
        /* draw the main screen exactly as today, into layers.main_view() */
    }
    if plan.draw_sheet {
        sheet_list.clear();
        drawer.render_sheet(&mut sheet_list, &draw_ctx);
        layers.render_sheet(ctx.device(), ctx.queue(), &sdf, &sheet_list, &fonts);
    }
    layers.composite(ctx.device(), ctx.queue(), frame.view, &drawer, s);
}
```

The main screen is drawn into its texture by whatever the app does today
(the companion's panel pass then the SDF pass with a load), with only the
target changed. Each layer render submits its own encoder (section 2,
"one renderer, one set of buffers").

**Sizes.** Both textures are in the surface format, with
`RENDER_ATTACHMENT | TEXTURE_BINDING`, one mip level, one sample.

- main: the surface size, `W x H` physical pixels;
- sheet: `ceil(extent * scale)` across the edge by the surface's size along
  it (Left and Right: `ceil(extent * s) x H`; Top and Bottom:
  `W x ceil(extent * s)`).

**When the textures exist** is section 4: created on the first frame
with `t > 0` (or pre-warmed at an edge-zone `Down` or an `open()` call, so
the allocation is not on a frame being shown), freed on the frame `t`
returns to 0 unless the app asks to keep them warm.

**Recreation.** `prepare` recreates a texture when its wanted size or the
format differs from what it has: a resize, a rotation, a change of scale
factor (DPI) that changes the extent, or a new surface format after an
Android resume. A recreated texture has no valid contents, so its
`drawn_at` is cleared and the plan asks for it to be drawn. `t` is kept
across a recreation; the sheet's position is a share of the new extent.

**Memory.** Four bytes per pixel (RGBA8 or BGRA8):

| Surface | Main | Sheet (Left/Right, default size) | Total |
|---|---|---|---|
| 1080 x 2340, scale 2.625 | 10.1 MB | 918 x 2340: 8.6 MB | 18.7 MB |
| 1440 x 3088, scale 3.5 | 17.8 MB | 1224 x 3088: 15.1 MB | 32.9 MB |
| 2560 x 1600, scale 2.0 | 16.4 MB | 720 x 1600: 4.6 MB | 21.0 MB |

The worst case is a Top or Bottom drawer at full extent: twice the
surface. This memory is held only while the drawer is visible (and during
an optional keep-warm window after it closes, section 4).

**Invalidation.** A layer is drawn when its texture is new or its mark's
revision differs from the one it was last drawn at:

- **main**: `layers.main_mark()`, bumped by the app whenever its main
  screen's drawing changes (the companion already knows: its screens
  return `drew`). With `MainUpdates::Frozen`, main is drawn once when the
  drawer leaves Closed and then not again until it closes, whatever the
  mark says; the terminal behind a frozen drawer stops moving.
- **sheet**: `drawer.content_mark()`, bumped by the drawer itself when
  the content router took an event (`DrawerRoute::Drawer` with a response
  that was not `ignored`, and every hover change), when the content
  router's `advance` returns true (a fling, a spinner, a fading
  indicator: content that animates inside the open drawer is redrawn into
  its texture every frame it moves), on `set_viewport`, and by the app for
  anything else it changes in the content.

Marking too often costs one redraw of that layer; marking too rarely shows
a stale frame, so where in doubt the drawer marks.

**While idle and open**, nothing changes and the frame is the composite
alone. The app may also skip presenting a new frame when `advance`
returned false and neither mark moved; that is the app's choice, as today.

### 3.8 Input

`Drawer::deliver(event)` answers with:

```rust
#[derive(Clone, Debug, PartialEq)]
#[non_exhaustive]
pub enum DrawerRoute {
    /// Not the drawer's: route it to the main screen as usual.
    Main,
    /// The drawer used it. Carries the content router's response when the
    /// content got it.
    Drawer(Option<EventResponse>),
    /// The drawer has taken over a press the main screen had: end the main
    /// screen's press now (for a Router, `Router::cancel_press()`), then
    /// treat this as `Drawer`.
    TookFromMain,
}
```

By phase (positions in viewport pixels; the slop is the theme's
`scroll.touch_slop`; "along the axis" means the dominant axis of the
movement since the press, `|dx| >= |dy|` for Left and Right, is the
drawer's):

- **Closed.**
  - A `Down` inside the edge zone (the strip `edge_zone` wide that starts
    `edge_inset` in from the drawer's edge), with `swipe_to_open`, starts
    a candidate; the `Down` itself is `Main`, so a tap at the very edge
    still reaches what is there.
  - While the candidate is within the slop, `Main`. When it first passes
    the slop along the axis towards open, the drawer takes it:
    `TookFromMain`, phase Dragging from `t = 0`, `Shown { by: EdgeSwipe }`.
    The drag starts from the point where the slop was passed, so the sheet
    does not jump by the slop. Past the slop in any other direction, the
    candidate is dropped and the press stays `Main`.
  - Everything else is `Main`.
- **Dragging.** Every pointer event is `Drawer`. `Up` releases (section
  3.4); the `Click` that follows is dropped. Back or Escape cancels the
  drag and closes (`Back`/`Escape`). Other keys are `Drawer(None)`.
- **Opening or Closing.** A `Down` anywhere catches the sheet (section
  3.4) and is `Drawer`. Back and Escape close (turning an Opening round).
  While Opening, other keys go to the content; while Closing, they are
  `Main`. Other pointer events are `Drawer` (nothing under a moving sheet
  is pressed).
- **Open.**
  - A `Down` inside the sheet goes to the content router, mapped to sheet
    coordinates; so does everything of that press while it is the
    content's. The drawer watches it: when it first passes the slop along
    the axis **towards closed**, the drawer takes it unless the content
    keeps it, which it does when the grabbed node claims the drag
    (`HostedControl::claims_drag`) or a scroll pane above the grabbed node
    can move that way (the scroll pane plan's innermost-pane rule, asked
    through a new crate-internal `Router::drag_stays_inside(delta)`). When
    the drawer takes it, it ends the content's press itself
    (`cancel_press` on the content router) and goes Dragging from `t = 1`;
    the route is `Drawer`. So in a Left drawer of vertical lists, a
    leftward swipe closes it and a vertical one scrolls; in a Bottom
    drawer, a downward swipe scrolls the list until it is at its top and
    closes the drawer from there (decided at the slop, not handed over in
    the middle of a gesture).
  - A `Down` on the scrim (outside the sheet) starts a scrim candidate:
    released within the slop, it closes the drawer if
    `dismiss.scrim_tap` (`ScrimTap`); dragged past the slop towards
    closed, it drags the sheet if `dismiss.drag`. Every scrim event is
    `Drawer`: the main screen takes no input while the drawer is open.
  - Wheel and trackpad over the sheet go to the content; over the scrim
    they are consumed.
  - Keys go to the content router, so Tab cycles within the drawer (focus
    is trapped as in a modal). On reaching Open, focus moves to
    `with_initial_focus`'s node if one was given. Back and Escape close
    (`Back`, `Escape`) if allowed by `dismiss`; if the content took the
    key first (a modal stack inside the content closing its own dialog),
    the drawer stays open.

**Ending a press in the main screen.** `Router::cancel_press(&self)`
becomes public (additive): it delivers an `Up` for the held button at the
last pointer position to the grabbed node, so its own bookkeeping ends,
lets go of the grab, and marks the press so its `Click` is dropped. It is
the scroll pane's "take the press from the node" made callable from
outside. The press feedback plan (Draft) names the same method for the
same purpose and would add clearing `PRESSED` and starting its fade to it;
the two agree.

A screen that routes its own touches (the companion's overview) ends its
press its own way on `TookFromMain`.

### 3.9 The composite pipeline and its uniform

Built in libcontrols on `wgpu` (src/drawer/composite.rs and
src/drawer/composite.wgsl), the way libmsdf's `BlurPass` is built: one
render pipeline for the surface format with `REPLACE` blending, no vertex
buffers (a full-screen triangle from `vertex_index`), a linear
clamp-to-edge sampler, one 96-byte uniform buffer, and a bind group of
{uniform, main view, sheet view, sampler} made when a texture is
(re)created, not per frame. Per frame it costs one `queue.write_buffer` of
96 bytes and one render pass with one draw of three vertices, recorded
into its own encoder and submitted after the layers' submits.

```rust
/// The composite's uniform; mirrors `Uniforms` in composite.wgsl field for
/// field.
#[repr(C)]
#[derive(Copy, Clone, Debug, Default, PartialEq, bytemuck::Pod, bytemuck::Zeroable)]
pub struct CompositeParams {
    /// [target_w, target_h, t, edge (0 left, 1 right, 2 top, 3 bottom)]
    pub target: [f32; 4],
    /// The sheet at t = 1, physical px: [x, y, w, h].
    pub sheet_open: [f32; 4],
    /// [shift_px at t = 1, scale at t = 1, corner_radius_px, 0]
    pub main: [f32; 4],
    /// Scrim colour, alpha at t = 1.
    pub scrim: [f32; 4],
    /// [shadow reach px, shadow alpha at t = 1, 0, 0]
    pub shadow: [f32; 4],
    /// What shows where the scaled main screen does not reach.
    pub clear: [f32; 4],
}
```

`t` is the only field that changes during a transition; everything else
changes on a resize or an options change. (`bytemuck` becomes a direct
dependency too; libmsdf already brings it, version 1.)

The pass draws one full-screen triangle into the frame. For each pixel
`p` (physical pixels, centre of the pixel), from `t` and the parameters:

1. **Main.** `c = viewport centre`, `dir` = the unit vector towards open
   (Left: +x). `q = c + (p - c - dir * shift_px * t) / mix(1, scale, t)`.
   The colour is the main texture at `q` if `q` is inside it, else the
   clear colour.
2. **Scrim.** `colour = mix(colour, scrim.rgb, scrim.a * t)`.
3. **Shadow.** With `e` the signed distance from `p` to the sheet's open
   edge outside the sheet, `colour *= 1 - shadow_alpha * t * (1 - e / reach)²`
   for `0 <= e < reach`.
4. **Sheet.** `o = sheet_open.pos - dir * extent_px * (1 - t)`; if `p` is
   inside the rounded rectangle at `o` of the sheet's size (rounded on the
   open edge's corners by `corner_radius`, anti-aliased over one pixel),
   the sheet texture at `p - o` is laid over with its alpha.

Sampling is linear with clamp-to-edge, `textureSampleLevel` at LOD 0 (the
textures have no mips; the same reason the SDF shader gives at
sdf_render.wgsl:546). At rest (`t` in {0, 1}, `scale` 1, `shift` 0) the
sample points are texel centres and the composite reproduces both
textures exactly; while moving, the sheet's offset is fractional and its
text is filtered for those frames. Offsets are not snapped to whole pixels,
which would make the motion step.

### 3.10 Fallback: direct drawing

Without `DrawerLayers` (an app that has not set it up, a test, a target
where the app chooses not to), the app draws its main screen into its list
as today and then calls `drawer.draw_direct(&mut list, &ctx, main_start)`,
which:

1. moves the main screen's instances (those from `main_start`) by
   `dir * shift * extent * t` with `DrawList::translate_from`
   (drawlist/mod.rs:655), when `shift` is not 0;
2. pushes the scrim as a box over the viewport with alpha `scrim.a * t`;
3. pushes the sheet's background with `push_fill(.., Elevation::Raised)`
   (drawlist/mod.rs:855) for its shadow;
4. `push_clip(sheet(t))`, `push_translate(sheet(t).pos())`, the content
   router's `render`, then `push_translate_end`, `push_clip_end`.

The main screen's `scale` is not drawn (a `DrawList` has translate and
quarter-turn rotation scopes, no scale), and every transition frame redraws
both screens in full: correct, but the cost the layers exist to avoid.
Input is identical in both paths.

## 4. Zero GPU cost on the main view

This is the owner's condition: while the drawer is fully closed it must
add nothing on the GPU, and the main view must reach the surface exactly
as it does today.

### 4.1 It is possible without always rendering the main view to a buffer

The main screen is rendered **every frame it is shown** in today's apps
anyway (the companion rebuilds and renders its list each frame,
lib.rs:2623-2681). So the main view never needs to live in a texture
while closed: on the first frame with `t > 0`, the app renders the main
screen into the main texture **instead of** into the surface, which costs
the same as that frame's ordinary render, and then the composite runs. No
frame before it pays anything, and no main-view content has to be carried
over from an earlier frame.

So, by phase:

| `t` and phase | GPU work beyond today's frame | Memory |
|---|---|---|
| 0, Closed, not moving | **none**: `LayerPlan::direct`; the app draws to the surface as today; the drawer records no pass and touches no texture | none (or the warm textures, 4.3) |
| first frame `t > 0` | the main render is redirected into the main texture (same cost), the sheet is rendered once (sheet-sized), one composite pass | both textures |
| `t > 0`, moving, sides unchanged | one composite pass only (both layers reused) | both textures |
| `t > 0`, a side changed | that side's render into its texture, plus the composite | both textures |
| frame where `t` reaches 0 | none: `direct` again; main goes back to the surface | freed or kept warm (4.3) |

`direct` is decided from the state alone (`phase == Closed`), before the
app draws anything, so there is no frame in which the main view is drawn
twice. An edge-zone `Down` that has not passed the slop leaves `t` at 0,
so a tap at the edge costs nothing either.

The drawer's CPU cost while closed is one phase check per frame and, per
pointer event, a test of whether a `Down` is in the edge zone.

### 4.2 What always rendering the main view to a buffer would cost

Had the design needed the main view in a texture every frame (so the
composite could start without a first-frame redirect), every frame of the
app's life would pay, on a 1080 x 2340 phone:

- **bandwidth**: the main pass writes 10.1 MB to the texture and the
  copy-or-composite reads 10.1 MB and writes 10.1 MB to the surface, about
  20 MB more per frame than today, 1.2 GB/s at 60 Hz (1440 x 3088: about
  2.1 GB/s). On a phone's shared LPDDR this is the single largest power
  cost of a simple UI and keeps the GPU out of its low clocks;
- **memory**: 10-18 MB held for the app's life;
- **latency**: none added (same frame), but the extra pass is on the
  critical path of every frame, including the scroll pane's flings and the
  terminal's updates, which today draw straight to the surface;
- **the rest of the framework**: every other control and the scroll pane
  would be drawn into an intermediate target; nothing breaks, but tile-based
  GPUs (Mali, Adreno) lose their direct-to-framebuffer path and must
  resolve the main texture to memory every frame.

That is not acceptable for a component that is closed most of the time,
and section 4.1 shows it is not needed. **This plan does not do it.**

### 4.3 When the textures exist

| Choice | First open | Reopen soon after closing | Memory while closed |
|---|---|---|---|
| Create on the first `t > 0` frame, free at `t = 0` | allocation on a shown frame (a few ms on some mobile drivers: a possible hitch) | the same hitch again | none |
| Pre-warm at an edge-zone `Down` or `open()`, free at `t = 0` | allocated during the slop or before the next frame, normally off the first shown frame | the same | none |
| Pre-warm, and keep warm for N s after closing | as above | none | the textures, for N s; no GPU work |

**Recommendation:** pre-warm at an edge-zone `Down` (with
`swipe_to_open`) and in `open()`/`toggle()`/`set_open_now(true)`; free on
the frame `t` returns to 0 by default (`DrawerOptions::keep_warm: f32`,
default 0.0 s). An app that opens
its drawer often sets `keep_warm` to a few seconds; that holds memory, not
GPU work. A pre-warm whose candidate never becomes a drag is freed when
the press ends. Pre-warming creates textures only (`create_texture` has
no contents to fill); nothing is drawn until `t > 0`.

### 4.4 Alternatives considered

1. **Main view always in a texture** (4.2): rejected, cost on every frame.
2. **No textures: redraw both sides every transition frame**, offset by a
   translate (the fallback, section 3.10), or by a render-pass viewport or
   scissor offset. Zero cost at `t = 0` as well, but every transition and
   open frame costs a full SDF render of both sides (pixels x commands,
   sdf_render.wgsl:378), the main screen cannot be scaled, and a viewport
   offset would need a libmsdf change (its pass sets no viewport and its
   shader works in target pixels). Kept as the fallback for apps without
   `DrawerLayers`, not as the main path.
3. **Main in a texture only during transitions, sheet drawn directly over
   it**: saves the sheet texture, but the sheet is re-rendered every
   moving frame. The sheet texture is smaller than the main one; keeping
   it is the cheaper choice for any sheet with text.
4. **This plan: textures only while `t > 0`, main redirected on the first
   frame, freed at `t = 0`.** Recommended.

### 4.5 libmorph and libmsdf

Neither needs a change. libmorph already gives the app what the drawer
needs (device, queue, surface view, format and size, app.rs:10, 87;
context.rs:76-132), and the drawer takes them as `wgpu` references from
the app, so it does not depend on libmorph. libmsdf's public renderer
calls are enough to draw the sheet with a transparent clear (section 2).

An optional later libmorph addition, not part of this plan:
`MorphContext::system_gesture_insets()` (Android
`WindowInsets.Type.systemGestures()`) and a way to set gesture exclusion
rectangles (`View.setSystemGestureExclusionRects`, at most 200 dp of each
edge's height), so an edge swipe can coexist with Android's back gesture
(risk 1).

## 5. Out of scope

- More than one drawer per screen at once (a Left and a Right drawer can
  each be a `Drawer`, but this plan does not arbitrate between them).
- Persistent (side-by-side, non-modal) drawers and a rail, M3's other
  navigation forms.
- Snap points (a half-height bottom sheet); `t` has two rest points.
- Blurring the main screen behind the scrim (`BlurPass` could do it as a
  later option).
- A full-screen dialog over an open drawer: a modal stack inside the
  content draws inside the sheet; one over everything is a third pass the
  app draws after the composite (open question 8).
- Right-to-left layouts (Start and End edges).
- Multi-touch: one pointer, as the router.

## 6. Tests

- **Easing** (src/ease.rs): each `CubicBezier` constant hits (0, 0) and
  (1, 1), is monotonic over 1000 samples, and matches reference values at
  x = 0.25, 0.5, 0.75 to 1e-4; `hermite_ease` with `m0` in {0, 1.5, 3}
  starts at slope `m0`, ends at slope 0 and never leaves [0, 1].
- **State**: `open()` from Closed reaches Open in `0.300 s` of `advance`
  with `t` exactly 1, emitting `Shown`, `Opened`; `close()` halfway through
  opening turns round and takes `max(0.12, 0.25 * t0)` s; `open()` while
  Open does nothing; `set_open_now` jumps without events other than
  `Shown`/`Opened` or `Closing`/`Hidden`.
- **Geometry**: `sheet()` for each edge at `t` in {0, 0.5, 1}; the
  default sizes; `set_viewport` keeps `t` and bumps the content mark.
- **Edge swipe**: a `Down` in the zone and a `Drag` past the slop towards
  open returns `Main` then `TookFromMain`, and `t` follows the finger past
  the slop point; a `Down` outside the zone never opens; a drag along the
  other axis stays `Main`; `edge_inset` moves the zone; a tap in the zone
  reaches the main screen.
- **Release**: lifting past half opens; lifting before half with a fling
  of 500 px/s towards open opens (`Fling`); a fling of 500 px/s towards
  closed from 0.8 closes; a finger resting 100 ms before lifting does not
  fling; the release duration and start slope match section 3.4 for given
  `t0` and `v`; no frame overshoots.
- **Open input**: a tap on a button in the sheet activates it with
  positions mapped to sheet coordinates; a scrim tap closes (`ScrimTap`)
  and never reaches the main screen; a leftward drag on a button in a
  Left drawer closes it and the button does not activate; a vertical drag
  on a vertical scroll pane in the sheet scrolls it; a drag on a slider in
  the sheet moves the slider; in a Bottom drawer, a downward drag on a
  list at offset 0 drags the sheet, at offset 100 scrolls the list; Back
  closes; Back with `dismiss.back = false` is `Drawer(None)` and leaves it
  open.
- **Catching**: a `Down` while Closing stops the sheet and drags it.
- **`Router::cancel_press`**: the grabbed button gets an `Up`, the grab is
  gone, the `Click` is dropped and the button does not activate.
- **Marks**: content input and a content fling bump the content mark; a
  drawer at rest bumps nothing; `MainUpdates::Frozen` asks for main once.
- **Composite parameters**: `composite_params(scale)` for each edge, at a
  scale of 2.625, against hand-computed values.
- **Layer planning** (pure, no device: the size and plan logic is a
  function of sizes, marks and phase): Closed is `direct` and asks for no
  texture; an edge-zone `Down` within the slop leaves it `direct`; the
  first visible frame draws both; an unchanged frame draws neither; a
  resize draws both; the frame `t` reaches 0 is `direct` and frees the
  textures with `keep_warm` 0, keeps them for `keep_warm` otherwise.
- **Fallback**: `draw_direct` pushes the scrim with alpha `0.32 * t`, the
  sheet's instances inside one clip and one translate at `sheet(t)`, and
  moves the main instances by the shift.
- **GPU check**: `examples/drawer_layers.rs`, headless wgpu, renders a main
  screen of labels and a sheet of buttons through `DrawerLayers` at `t` in
  {0, 0.25, 0.5, 1} for Left and Bottom, writes PNGs to
  `out/drawer/<YYYYMMDD_NN_name>/` with a log entry, and checks: at `t = 0`
  no layer texture exists and the frame equals a plain render of the main
  screen; at `t = 1` with no scrim the sheet's rectangle equals the sheet
  texture texel for texel; at `t = 0.5` the sheet's leading column is at
  `extent / 2`; the scrim darkens by `scrim.a * t`.

## 9. Risks

1. **Android's system gestures own the edges.** With gesture navigation,
   a swipe in from the left or right edge is Back and one up from the
   bottom is Home; the app may never see the touch. Mitigations: an
   `edge_inset` to start the zone inside the gesture area, an app button
   that calls `open()`, and (optional, libmorph) gesture insets and
   exclusion rectangles (section 4). A Bottom drawer opened by swipe will
   not work well on gesture navigation at all.
2. **Memory** on high-resolution phones: up to about 33 MB while visible
   (section 3.7), freed when it closes by default.
3. **An allocation hitch on the first frame** of an opening, on drivers
   that are slow to create large textures; mitigated by pre-warming
   (section 4.3), removed by `keep_warm` at a memory cost.
4. **Shared renderer buffers.** Rendering two layers into one encoder with
   the `_into` variants would draw the second list twice (section 2). The
   plan and the README say to use the self-submitting calls; the GPU
   example exercises the order.
5. **Colour space.** With an sRGB surface the layers are sRGB textures;
   sampling decodes to linear and the scrim is blended in linear space,
   which looks lighter than the same alpha drawn by the SDF shader (the
   modal `Backdrop`). The default scrim alpha may need tuning on the
   device.
6. **Softened text while moving.** The sheet is sampled at fractional
   offsets during motion; it is exact at rest.
7. **Stale layers.** A main screen that changes without the app bumping
   `main_mark` shows a stale frame behind the scrim until something else
   bumps it. Marking is cheap; the README says to mark when in doubt.
8. **Overlap with the press plan's `cancel_press`.** If the press plan
   lands first with a different signature, this plan uses that one.

## 10. Open questions for the owner

   They could sit behind a `gpu` feature (on by default) so a CPU-only
   user of libcontrols does not see `wgpu` in its API; wgpu is compiled
   through libmsdf either way.
2. **Drawer values in `DrawerOptions` (additive, 0.9.2) or a

4. **Edges**: Left, Right, Top, Bottom; or Start and End for
